# Connected showroom editing and lounge game

## Goal

Let a shop owner or authorized staff member arrange the shop's displayed shoes on the existing fixed 3D shelf slots, persist each move immediately, and show that arrangement to customers. Replace showroom branding that says `SOLESPACE` with the current shop name. Let visitors approach a couch with WASD, press `E` to sit, and play a local casual XOX game against a bot.

## Approved decisions

- Use the existing public showroom URL. Editing controls appear only when the authenticated actor owns the displayed shop or is staff linked to that shop.
- Save automatically after every successful drop.
- Dropping onto an occupied slot swaps the two products.
- Couch seating is proximity-based: approach with WASD and press `E`.
- The XOX opponent uses casual/random legal moves.
- Game state is local to the visit. No leaderboard or game-history persistence is needed.

## Recommended approach

Keep the current Three.js room and its fixed geometry. Give every showroom slot a stable key, expose those slots as raycast targets in edit mode, and keep the persisted data as product-to-slot assignments. A small server endpoint performs an atomic move/swap and returns the canonical assignments. This avoids a new drag-and-drop dependency, arbitrary 3D coordinates, and layouts that can drift away from the authored shelves.

The owner editor uses pointer drag in the 3D scene. The selected shoe and valid shelf targets are highlighted while dragging. A click/keyboard move path remains available for people who cannot use a continuous pointer drag. Furniture and room geometry are not editable.

## Data and server behavior

### Placement storage

Add a `showroom_product_placements` table with:

- `shop_owner_id` (foreign key to the shop owner);
- `product_id` (foreign key to the shop's product);
- `slot_key` (the stable key generated by `showroomLayout`);
- timestamps.

Enforce one product and one slot per shop with unique constraints on `(shop_owner_id, product_id)` and `(shop_owner_id, slot_key)`. Placement records are only for products currently eligible for the showroom; missing records continue to use the existing deterministic product order for unassigned products.

### Authorization and endpoint

Add an authenticated placement endpoint under the existing shop-owner API surface. It accepts a product ID and target slot key, derives the tenant from the authenticated `shop_owner` or `user` actor, and never trusts a client-supplied shop ID. The action must verify:

1. the actor is the shop owner or a linked active staff account for that shop;
2. the actor has the existing retail product-management/upload permission used by staff product operations;
3. the shop has an active showroom-entitled retail subscription;
4. the product belongs to the resolved shop and is eligible for display;
5. the target slot is a valid slot within the shop's current entitlement.

The move/swap runs in a database transaction. If the target is occupied, the target product receives the source slot and the moved product receives the target slot. The response returns the canonical placement list so the client can reconcile after concurrent edits or a retry. Validation or authorization failures leave all records unchanged.

The showroom page payload adds the canonical placement list and a `can_edit_showroom` flag. Customers continue to receive the arrangement but never receive editing controls. The existing premium access middleware remains the gate for entering an entitled showroom.

## Frontend and scene behavior

### Product placement

Extend the existing layout slot type with a stable key while preserving the authored positions and capacity rules. The showroom maps persisted assignments first, then fills unassigned eligible products into remaining slots using the existing deterministic order.

When `can_edit_showroom` is true, show a compact edit toggle and save status. Dragging a shoe card/mesh highlights valid slots. Dropping on a slot updates the local arrangement optimistically, sends the placement request, and keeps the result only when the server confirms it. A failed request restores the previous arrangement and reports the error. Edit mode is disabled during a pending save for the same product to prevent duplicate moves.

Provide an accessible move fallback that selects a shoe and then a named shelf slot from the existing UI, with the same server action and swap behavior. This is a fallback for keyboard and touch use; it does not add a second layout model.

### Shop branding

Pass the shop's resolved display name from the Inertia page into `VirtualShowroom` and `createShowroomScene`. Use it for the HUD and every authored sign currently hardcoded as `SOLESPACE`. Keep the existing subtitle/copy and use a short safe fallback only if the shop name is empty. The document title already uses the shop name.

### Couch seating

Expose a seat interaction point for each existing lounge. The point sits in the walkable area in front of the couch so the current furniture colliders do not trap the player. While the player is within the interaction range, show an `E Sit` prompt. Pressing `E` moves the camera to the seat-facing pose, freezes walking/looking, and marks the visitor as seated. A visible `Stand up` action and `Escape` keyboard path leave the seat and restore the prior camera/movement state.

The same interaction works for customers, owners, and staff while they are visiting the showroom. Owner/staff editing controls remain independent of seating.

### XOX game

Render a small showroom-styled overlay after seating. The visitor is `X`, the bot is `O`, and the bot chooses a random legal square after a short UI delay. Show turn/status text, win/draw result, `New game`, and `Stand up`/close controls. Resetting or leaving the couch clears only the local game state. No network request is made for game moves.

## Accessibility and responsive behavior

- Keep all edit, sit, stand, and game actions reachable by keyboard.
- Use the existing high-contrast button treatment and touch targets of at least 44px.
- Respect reduced-motion preferences when animating the camera into or out of the seat.
- On narrow screens, keep the game and edit status overlays inside the viewport; do not add a separate mobile layout model.

## Verification

Add focused tests for:

- stable slot keys and placement ordering/swap helpers;
- placement endpoint validation, owner/staff same-shop authorization, cross-shop denial, and transaction behavior;
- dynamic shop-name propagation and edit flag rendering;
- couch interaction state transitions;
- casual bot legal moves, win detection, draw detection, and reset.

Run the focused showroom tests, Laravel feature tests for the endpoint, the production frontend build, and a browser check covering owner/staff drag-and-drop, refresh persistence, customer read-only rendering, `E` couch seating, and one complete XOX round.

## Out of scope

- Freeform furniture or room editing;
- arbitrary shoe coordinates outside authored shelf slots;
- changing premium slot limits or subscription rules;
- product catalog redesign;
- online multiplayer, leaderboard, or game-history storage;
- new frontend dependencies.
