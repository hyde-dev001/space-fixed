# Terms Policy Editor and Flow Separation Plan

## Goal

Make the Shop Settings Terms and Conditions Policy editor easier to understand and maintain while keeping one shared Refund and Payment policy for both customer flows. Retail-specific terms must appear only in retail checkout, and repair-specific terms must appear only in repair submission/payment.

## Acceptance criteria

- `Refund and Payment Terms` is visibly shared by Retail and Repair.
- `Retail Terms`, retail-scoped custom sections, and legacy retail custom sections are shown only in retail checkout.
- `Repair Service Terms` and repair-scoped custom sections are shown only in repair submission/payment.
- Existing policy text and custom-section metadata survive loading, saving, and publishing.
- The editor presents the primary text fields without requiring an accordion or clause-builder click for every section.
- Existing draft/publish behavior and policy-version acceptance records remain intact.
- Buttons, tabs, checkboxes, radios, toggles, and active states in the affected settings controls use the system black/white/gray palette; semantic error/success feedback remains distinguishable.
- Tablet/mobile layouts remain usable by stacking the same content without changing the payment or acceptance behavior.
- Payment and repair policy tests cover flow-specific filtering and acceptance compatibility.
- A fresh `public/build` is generated and tracked.

## Implementation scope

1. Add a shared backend policy-section resolver for `retail` and `repair` flow filtering, preserving shared terms and filtering scoped custom keys and metadata. Keep the unscoped active-policy response backward compatible unless a flow is requested.
2. Update the active-policy API and customer consumers to request the correct flow. Keep the same published policy version ID and content hash for acceptance evidence.
3. Fix the settings editor normalization so base keys are retained, while preserving legacy custom-key compatibility. Replace the click-heavy primary editor presentation with a shared section plus channel-specific cards/fields; retain optional custom-section editing and the existing draft/publish endpoints.
4. Apply existing SoleSpace black/white/light-gray visual tokens to affected controls, including the settings toggle component used on this page.
5. Add/adjust focused frontend and backend tests for section resolution, editor persistence, retail/repair API filtering, and acceptance payload compatibility.
6. Run focused tests, frontend tests, `git diff --check`, browser verification when the local app is runnable, and the production build. Review the diff for unrelated changes, then commit and push the feature branch.

## Risks and safeguards

- Do not alter policy version tables, acceptance columns, or acceptance IDs.
- Do not discard hidden channel content when saving from a channel-focused editor; submit the complete in-memory policy payload.
- Treat legacy `custom_terms_` keys as retail for a `both` shop so old retail entries cannot leak into repair. Preserve repair-only legacy behavior only where existing stored policy scope requires it.
- Keep API filtering server-side and mirror it in the frontend modal as defense in depth.
- Preserve unrelated worktree changes and stage only intended files plus generated build output.
