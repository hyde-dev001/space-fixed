# Parcel incident recovery implementation plan

> For agentic workers: execute sequentially in this worktree. Implementation and subsequent commit/push with a fresh public/build are authorized. Do not dispatch agents, merge or deploy without separate authorization.

**Status:** Bounded implementation authored and locally verified sequentially in this worktree; release verification remains open below. D1-D10 remain the approved business-rule baseline in [the aligned specification](../specs/2026-10-27-parcel-incident-recovery-design.md). **D9 is approved but deferred; active scope is D1-D8 and D10.** The user subsequently authorized commit and push, including a fresh `public/build`. Merge, deployment, provider/live operations and production data repair remain unauthorized. Decisions are not reopened. Earlier output-local diagnostics remain historical audit evidence.

**Goal:** make every eligible incident decision executable through custody, source-specific receipt/inspection/disposition and authorized closure, while preserving existing money, source and batch workflows.

**Architecture:** keep `DeliveryIncident` as the recovery record. Extend its decision/eligibility behavior and existing source, custody, proof, refund and repair services. A small incident recovery coordinator serves existing source workspaces; it owns no separate return, refund, stock or payment ledger.

**Tech stack:** current Laravel 12/PHP 8.2, Inertia 2, React 18/TypeScript, existing Tailwind/UI components, pnpm, PHPUnit/Vitest. No new dependency, queue engine, enum values or media assets.

## Acceptance contract and reach

- All 15 IDs retain traceability; five NOT TESTED cases gain explicit approved rules and independent execution evidence before sign-off.
- PD-03/VR-04/CD-04 show one same-shop recovery item even without a refund or prior failed attempt; actual shop receipt, inspection and supported next disposition are executable.
- Both retry routes require valid Dispatcher schedule/window/eligible rider, new assignment identity, explicit acceptance, correct possession, current proof and normal operational gates. Original failure/assignment/batch history remains.
- Still-batched stop incidents cannot create unusable standalone offers. Mixed retail/repair batch recovery preserves unaffected work, snapshots, holds/capacity and source identity.
- Missing/unsafe/unresolved-dispute parcels cannot start unsupported movement. Logistics OFF denies new movement; existing permitted physical closing operations remain executable.
- Neither verdict, receipt nor inspection falsely completes sale/repair/refund/incident. Existing approvals, captured/COD balance, inventory, compensation and fee services remain authoritative and idempotent.
- Tenant, RBAC, attendance, maker-checker, private evidence and audit guards apply to new endpoints, projections and notifications.
- D6: Dispatcher operational closure requires a verified operational outcome/final disposition; pending Finance/refund/claim/source obligations remain independently visible, owned and actionable. No overall-complete claim until all required linked work completes.
- D9 is deferred: preserve all existing Shop Owner functionality and authorization. No new Owner physical receipt/release, actor fields, custody participant migration, permissions, authentication, roles, dashboards, routes, buttons or notifications. Scenarios requiring that functionality retain existing behavior and report the operational limitation; no fake employee or authorization bypass.
- D10: normal, retry and reassigned deliveries in standalone, previously batched and replacement-batch flows can arrive, upload/correct proof, undergo authorized review and complete after legitimate current-assignment/stop activation despite window expiry alone. Material pre-activation changes require renewed acceptance; post-activation schedule updates alone do not retroactively invalidate continuation.
- D4/D5/D7/D8: no duplicate original-parcel stock deduction or automatic fee; current warranty transport/customer arrangements retained; unsupported replacement/property-value settlement excluded in favor of actionable investigation/escalation; unsafe/partial goods retain actual quantities/evidence and safe custody.

Likely changes reach Dispatcher decision API/UI, Rider offers/current work/proofs, source Staff and Repairer workspaces, customer tracking/repair arrangement, source shipment adapters, notification routing, route capability catalog, relevant factories/tests and operational notes. Finance and Owner payment screens should need only existing links/projections, not replacement execution logic. Follow current caller graphs before each edit; preserve unrelated changes.

## Schema proposal and compatibility

One additive migration has been created and exercised only on disposable tests: nullable JSON `delivery_incidents.recovery_context`. It stores validated findings, receipt/inspection/readiness, source references, investigation/safekeeping and operational outcome. Existing assignment-linked `DeliveryEvent` records hold activation, effective schedule, previous schedule, revisions, action UUID and canonical facts hash. Pending obligations are read from their owning services rather than copied into a settlement flag in incident JSON. Raw paths/internal findings remain hidden; clients receive authorized projections. No custody participant or financial schema is added.

The inspected custody migration requires `requested_by_user_id` and allows nullable `released_by_user_id`/`received_by_user_id`, all user foreign keys. The model/controller/service currently accept User actors. Staff, Dispatcher, Repairer and Rider already use User identities; D2 can reuse these columns and current typed proof/event actors without a custody participant migration. Preserve historical actor/evidence rows and signatures. An Owner ID must never be substituted into a user FK or represented by a fabricated employee account; existing ShopOwner tenant parameters and proof/event capabilities do not grant new Owner authority.

No Owner actor fields or participant-schema widening are planned while D9 is deferred. Derive employee actors from authenticated User context; enforce exact source/tenant/transfer, phase/proof, distinct participants, attendance where applicable and replay checks under locks. An Owner session, including a simultaneous second guard, cannot supply the employee actor. Preserve all existing Owner functionality and operational authorization boundaries.

Dependency review: D2 extends source-aware User authorization/projections, not Owner authentication. Staff/Repairer receipt must commit without requiring the receiver to arrange an outbound transfer; current automatic staging uses the receiver in a Dispatcher-authorized request. Keep transfer request/cancellation Dispatcher-controlled and expose follow-up to that existing actor only after inspection/readiness and current dispatch authorization. No employee recovery path depends on D9, Owner notifications or the deferred migration. If no existing authorized receiver can serve a scenario requiring D9, preserve current behavior and record the operational limitation, without inventing an alternate identity or completion.

Reuse existing `decided_at`, `decided_by_user_id`, `decision_key`, `decision_facts_hash`, `revision`, `request_key`, `resolution`, `resolution_note`, `resolved_at` and actor IDs in events. Do not add another decision timestamp, generic task table, second incident enum, return table or refund table. Existing source-attempt and return uniqueness remain. Existing shop/status/type incident index is adequate initially; query count/plan evidence is needed before adding another index.

Persisted snapshot shape; earlier revisions and evidence remain in events:

```text
recovery_context:
  findings: verified condition/obstacle/dispute/customer arrangement and item identities
  evidence_paths: decision evidence; private receipt/inspection/investigation references are also retained
  execution_assignment_id: exact recovery assignment; superseded occurrences retain their successor link
  receipt: return proof, actual receiver, time and evidence
  inspection: actual items/quantities/condition, quarantine, actor/time and revision
  readiness: exact inspected revision, actor/time
  source_outcome: linked refund/repair/new shipment and leg IDs
  disposition: selected source action, actor/time, note and next owner
  investigation: append-only event-backed findings/evidence; no property settlement authority
  safekeeping_return_leg_id: supervised return after evidenced recovery of confirmed loss
  operational_outcome: verified outcome, Dispatcher closure actor/time and note
```

Action replay lookup is scoped to locked incident + stage + action UUID in existing events; canonical facts include actor, source, revision and evidence digest/reference. Under the incident/shop lock, return identical prior result or reject conflicting facts before writing. Existing decision/assignment/transfer unique keys remain separate. A materially revised decision appends an event and increments revision; do not lose older key/facts on the latest-row update.

No automatic historical backfill. Existing resolved incidents cannot be reclassified safely from assignment or return timestamps alone. A read-only reconciliation report may identify missing follow-up for human review; activating a historical recovery requires authorized evidence and a new recorded occurrence, preserving the old verdict/closure. Existing null-context payloads remain readable. Batch incidents keep their subject invariant and hold behavior.

Migration `up`: add nullable incident JSON only; retain old rows, user actor FKs, proof IDs and executable pending transfers. Run old/null/new context compatibility tests on disposable SQLite and MariaDB. Context `down` refuses non-null recovery history; never delete operational/evidence history to make rollback succeed. No Owner participant migration, actor-format change, financial settlement table or accounting migration is in scope. Deploying/rolling back remains outside current authorization.
